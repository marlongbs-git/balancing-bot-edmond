## Modules

| Module | Responsibility |
|---|---|
| `mpu6050.c/.h` | I2C driver for the IMU: register reads (16-bit values assembled with bit shifts), calibration, accelerometer pitch, gyro rate, complementary filter, I2C error handling and bus recovery |
| `robot_state.c/.h` | Builds one `RobotState` (x, v, θ, ω, tipped) from the IMU and encoder. Everything downstream reads this struct |
| `control.c/.h` | LQR gains, control effort, force-to-duty conversion, deadband handling, PWM and direction output |
| `ssd1306` + face code | OLED driver and the two face bitmaps. Redrawn only when the fallen/normal state changes |
| `main.c` | Peripheral init (generated by CubeMX) and the control loop |

## Control path

| Function | What it does |
|---|---|
| `getRobotState()` | Returns the latest fused state. Single entry point for sensor data |
| `updateOrientationState()` | Reads accel and gyro once each, runs `compFilter()`, stores θ and θ̇ |
| `compFilter(accelAngle, gyroRate, alpha)` | `θ = α(θ + gyro·dt) + (1−α)·θ_accel`. Guards the first call and clamps `dt` |
| `setControlGains(kx, kv, ktheta, komega)` | Loads the gains from the MATLAB LQR design |
| `computeControlEffort(&state)` | `u = -K·x`. Converts degrees to radians first, because K was designed in radians |
| `computeControlDuty(u, v)` | Turns a force into a duty cycle using the motor model (below) |
| `setPWMControl(duty)` | Sign sets the direction pins, magnitude sets the `TIM1` compare value |
| `updateFaceDisplay(tipped)` | Draws a face only on a state change, to avoid blocking the I2C bus |
| `printRobotState(&state)` | UART debug output for plotting |

### Force to duty

LQR outputs a force at the wheel. The motor needs a voltage, so:

```c
wheelOmega = v / r;                                  // wheel speed from cart velocity
torque     = u * r;                                  // force -> wheel torque
V          = (torque + ktkvOverR * wheelOmega) / ktOverR;  // add back-EMF term
duty       = V / supplyVoltage;                      // normalise to PWM
```

Motor constants (FIT0450): `Ra ≈ 2.14 Ω`, `Kt ≈ 0.028 N·m/A`, `Kv ≈ 0.336 V·s/rad`.

The motor constants were gathered using calculations from [DFRobot's FIT0450 Datasheet](https://wiki.dfrobot.com/fit0450/#tech_specs)

### Fall detection

If `|θ|` exceeds the tilt threshold, `state.tipped` is set, PWM goes to zero and the fallen face is shown. `updateFaceDisplay()` is called every loop (outside the tipped branch) so the face returns to normal once the robot is upright again.

```c
#define FALL_THRESHOLD_DEGREES 40.0f
#define RECOVERY_THRESHOLD_DEGREES 5.0f
```

## Setup and build

**Requirements:** STM32CubeIDE, an ST-LINK (built into the Nucleo), a serial terminal.

1. Clone the repo and open `firmware/` in STM32CubeIDE (*File → Open Projects from File System*).
2. Open the `.ioc` file to check the peripheral configuration. CubeMX is the source of truth for pins.
3. Build with the Release configuration (`-Os`), then flash with the green Run button.
4. Open a serial terminal on the ST-LINK virtual COM port, **USART2 at 38400 baud** 

Peripheral summary (see [`../electronics/pinout.md`](../electronics/pinout.md) for pins):

| Peripheral | Use |
|---|---|
| `I2C1` | MPU6050 and SSD1306 on one bus |
| `TIM1` CH1 / CH4 | Motor PWM |
| `TIM2` | Encoder interface |
| `USART2` | Debug prints |

## Running and tuning

1. Flash new robot code with the USB connected exclusively.
2. Remove USB Connector.
3. Power up with the robot held upright and still. The gyro offset is calibrated at startup.
4. Release it. It should hold itself near vertical.
5. Gains are set in one place via `setControlGains(...)`. Regenerate K in `matlab/` and paste the new values.

LQR tuning intuition: `Q` penalizes state error, `R` penalizes motor effort, and only their ratio matters. Raising the θ and θ̇ weights makes the robot react harder to tilt. Raising `R` makes it gentler and slower.

## Challenges

- **I2C failures.** Intermittent acknowledge-failure and arbitration-lost errors came from loose connectors. Soldering fixed the root cause; status checks, timeouts and bus recovery make the driver fail loudly. See [`../docs/i2c-debugging.md`](../docs/i2c-debugging.md).
- **Degrees vs radians.** The state is stored in degrees but K was designed in radians. Missing the conversion saturated the motors.
- **OLED blocks the sensor loop.** A full refresh sends about 1 KB over I2C and takes roughly 8 to 10 ms. The face is redrawn only on state changes.

## Known limitations

- Only one encoder is wired, so position and velocity come from a single wheel.
- No battery operation yet (bench supply plus 5 V buck converter).
- No driving command yet; the controller only holds the upright position.
- Complementary filter only; an EKF is on the roadmap.
